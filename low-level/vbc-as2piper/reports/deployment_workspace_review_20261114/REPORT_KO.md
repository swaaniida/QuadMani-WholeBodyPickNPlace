# 배포 목적 재검토 — 바닥 작업공간·정지 지지·속도 추종

## 결론

**이전 28k 추천을 실기 배포 추천으로는 철회한다.** 이전 선정은 추종 오차·roll 등의 비교였고 정지 조작에서 네 발 지지를 확인하지 못했다. 이번에는 실제 발 위치와 힘을 함께 계측해 RR 무접지를 확인했다. 검증한 주요 checkpoint를 배포 적합 모델로 판정할 근거가 없다. Checkpoint 교체만으로 해결할 문제가 아니다.

현재 모델에는 학습 범위에 바닥이 없고, 정지 조작의 네 발 지지를 요구하는 목적함수가 없다. 전진 reward는 과속에서 포화한다. 추가된 실제 손목 카메라 자산도 학습 당시 자산과 다르다. 새 배포용 학습에서는 이 조건들을 먼저 반영해야 한다.

**이번 작업은 읽기 전용 코드 검토·독립 평가·오프라인 기구학 계산이다. 기존 학습 코드/config/PPO/reward/checkpoint를 수정하지 않았고 학습을 실행하지 않았다.** 추가 파일은 이 report 디렉터리에만 있다. 현재 카메라 URDF도 되돌리지 않았다.

## 1. 반경·pitch 계산의 기준

세 가지 pitch는 구분한다.

- `φ`: 목표 위치의 구면 고도각. 음수면 구면 중심보다 아래쪽이다.
- `θ`: 몸통 pitch. 여기서는 **양수가 머리를 아래로 숙이는 방향**이다.
- `β`: UMI TCP의 world RPY pitch. 이 URDF에서 β180°는 TCP +Z축이 수직 아래, β160°는 아래 방향에서 전방으로20° 기울어진 접근이다. B1 Z1의 다른 축/roll offset을 그대로 복사하면 안 된다.

실제 arm base offset은 `a=(0.22435,0,0.1319)m`. 관측의 EE 위치는 계속 실제 arm base와 몸통 quaternion 기준으로 변환해야 한다. 관측 기준과 목표 샘플링의 가상 구면 중심을 같은 개념으로 취급할 필요는 없다.

현재 명목 서기에서 arm base 높이는 `0.3244069+0.1319=0.4563069m`다. 현재 r[0.40,0.48], φ[0.10,0.50]는 목표 z가 약0.496~0.686m여서 바닥을 포함하지 않는다.

### 현재 중심을 그대로 쓰고 음의 pitch만 추가하면 생기는 문제

실제 arm base의 높이는 `z_a=h+0.1319 cosθ−0.22435 sinθ`다. 몸통 높이를 유지하고25° 숙이면 arm base가 약10.72cm 내려간다. 서기에서 z=2cm로 샘플링한 목표가 arm base와 함께 내려가 **약−8.72cm**가 된다. `_collision_check`가 목표 생성 때 검사한 뒤 몸통 자세가 바뀌는 경우이며, 단순 반경 확대만으로 해결되지 않는다.

원본 B1은 실제 arm base 자체가 아닌 **가상 구면 중심**을 쓴다. XY는 base yaw/위치를 따르고 Z는 지면 기준0.7m로 고정된다. AS2에서도 **관측은 실제 arm base / 바닥 목표 높이는 지면·물체 기준 고정**으로 분리하는 편이 맞다. 실제 물체 접근 중에는 샘플링 시 정한 world 목표를 유지하고 현재 arm base 상대 좌표만 매 step 갱신해야 한다.

### B1과 비슷한 전방 바닥 명령 범위

AS2 가상 중심 후보를 명목 arm base 높이인 `c=(0.22435,0,0.4563069)m`로 잡으면, yaw0에서 다음 관계가 성립한다.

`x=c_x+r cosφ`, `z=c_z+r sinφ`.

| 바닥 TCP 목표 / 몸통 원점 기준 | 필요한 가상 r | 필요한 위치 φ |
|---|---:|---:|
| x0.45m, z0.02m | 약0.491m | 약−1.094rad /−62.7° |
| x0.75m, z0.02m | 약0.683m | 약−0.693rad /−39.7° |
| x0.85m, z0.02m | 약0.763m | 약−0.609rad /−34.9° |
| x0.90m, z0.02m | 약0.804m | 약−0.573rad /−32.9° |
| x0.95m, z0.02m | 약0.847m | 약−0.541rad /−31.0° |
| x1.00m, z0.02m | 약0.890m | 약−0.513rad /−29.4° |

원본 B1의 r최대0.95·중심z0.7은 z2cm에서 목표 x최대 약0.963m다. AS2의 r최대0.85는 약0.954m, r최대0.90은 약1.012m에 해당한다. **이 B1 수치는 명령 기하학 범위이며 B1의 모든 말단 포즈가 실제 성공했다는 검증값은 아니다.**

설계 후보는 **r[0.40,0.85], φ[−1.15,+0.65]rad**를 기본 전방 작업공간 포락선으로, **r최대0.90은 더 먼 바닥 접근의 추가 포락선**으로 잡을 수 있다. 현재값을 이 숫자로 단순 치환해 장시간 학습하라는 뜻은 아니다. r·φ·yaw·tool orientation을 함께 제한한 유효 영역과 경로가 필요하다.

### 실제 URDF의 전신 자세 + 6D IK + 충돌 검사

현재 D435i 포함 URDF, 총 명목 질량23.43034kg, 실제 TCP, 손가락 열림을 사용했다. 네 발은 초기 접지 위치에 유지하고 앞다리/뒷다리 IK를 풀었다. 그 뒤 팔6D IK, 비인접 collision 형상 및 지면 관통, 정적 CoM을 검사했다. 허용 침투1mm·CoM 여유20mm는 이번 설계 검사 기준이며 실기 안전 보증값이 아니다.

| 몸통 높이 | 전방 tilt | TCP 접근 β | 지면 TCP x 도달 예 |
|---|---:|---:|---:|
| 0.324m | 0° | 175° | 약0.60m, 어깨 joint 상한 근처라 여유 작음 |
| 0.30m | 20° | 160° | 약0.90m |
| 0.27m | 30° | 160° | 약0.95m |
| 0.27m | 30° | 150° | 약0.9875m |
| 0.27m | 35° | 150° | 약1.00m |

0.27m/30° 자세의 calf 각은 앞 약−2.475rad, 뒤 약−1.217rad로, **앞다리를 더 접고 뒷다리는 상대적으로 펴는 형태**다. 모든 다리를 같은 만큼 접는 crouch가 아니다. 명목 서기 높이0.324m를 유지한 채30° 이상 숙이는 자세는 검사한 고정 발 위치에서 뒷다리 관절 한계 때문에 성립하지 않았다. 몸통 높이와 pitch를 함께 설계해야 한다.

이 결과는 유한 표본에서 찾은 도달 예이며 전역 최대나 최소 필요 tilt의 증명이 아니다. IK 시작점에 따라 해를 찾는 각도가 달라질 수 있다. 특히150° 접근은 수직에서30° 기울어진 파지이므로 물체 형상·카메라 시야·접촉 과정까지 별도로 검증해야 한다. 수직 아래 접근175~180°를 고집하면 전방 최대 도달은 대체로0.84~0.88m 수준으로 줄었다.

### tool orientation도 함께 바꿔야 하는 이유

현재 `β=−φ+2.455216+δpitch`이고 δpitch는±0.08rad뿐이다. 가상 구면으로x0.95m/z2cm를 샘플링하면 기본 β약171.6°여서160° 접근에 필요한 δ약−0.20rad가 범위 밖이다. 가까운 바닥x0.45m는 기본 β약203°이고175°로 만들려면 δ약−0.50rad가 필요하다. **위치 pitch만 넓히면 원하는 바닥 tool pose가 생기지 않는다.**

초기 FK 정합용 상수2.455216을 무작정 바꾸지 말고, 초기 자세는 유지한 채 바닥 mode에서 원하는 world tool pitch150~175°를 먼저 정하고 해당 δpitch를 계산하는 방식이 적합하다. 이 각도 범위도 오브젝트별 접근 조건과 하드웨어 토크 제한으로 잘라야 한다.

550개 r/φ/yaw 표본에서 지면 아래125개를 제외한425개 중348개만 검사한 전신 자세에서 해를 찾았다. **77개/425개≈18.1%는 해를 찾지 못했다.** 따라서 하나의 사각 구면 범위 전체가 유효하다고 주장할 수 없다. 이 검사는 r최대0.85까지이며0.90 확장은 전방 단면의 별도 표본 검사만 했다.

원본 구면 표현·보간과 PPO를 유지하면서, 학습 밖에서 전신 가용 영역/경로를 검증하고 모드별 유효 영역을 샘플링해야 한다. 매 training step의 고비용 IK 재검사를 넣자는 제안은 아니다. 바닥 mode에서는 z와 r을 정한 뒤 `φ=asin((z−c_z)/r)`로 연동하면 바닥 표본을 의도대로 확보할 수 있다. 최종 지면 높이는 EE 목표 XY의 지면/물체 높이를 사용해야 하며 rough 전체 평균 높이로 대체하면 안 된다.

### 기구학 최대와 실제 사용 최대는 다르다

계산한 먼 포즈는 CoM 여유약8~9cm, 네 발에 양의 정적 지지력을 배분할 수 있었다. 한 정적 해의 발 하중은 앞 약92N씩/뒤 약22N씩이다. 뒷발을 띄워야만 바닥에 닿는 구조는 아니다.

하지만 같은 포즈의 URDF 중력 계산에서 **PiPER joint2에 약12.5~13.1Nm**가 필요했다. 이는 물체 질량·가속·접촉 반력을 제외한 한 IK 해의 계산값이다. 실제 PiPER 연속/피크 토크·열 한계는 확인되지 않았고 URDF의 effort100Nm는 검증된 모터 정격이 아니다. 따라서 위 도달값을 실기 운영 범위로 바로 확정하지 않는다. 실제 토크/속도/gain/지연 제한을 넣고 다시 잘라야 한다.

## 2. 오른 뒷발 무접지 검증

새 평가에서는 20k/28k/30k/45k 각각8개 환경, 64초 world-fixed EE 궤적, 모든 base velocity command0, DR/Push OFF로 실제 발 위치·net contact force를 reset 전에 기록했다. 학습 당시 URDF를 카메라 통합 전 exact-byte backup에서 report 디렉터리에만 복원해 사용했다. 발 이름은 실제 native body index를 검사했고 `FL/FR/RL/RR`가 맞았다.

아래는 바닥 구간12~60초,8개 환경 전체다. 발바닥 간격은 실제 foot center z에서 충돌 구 반경0.028m를 뺀 값이다.

|---|---:|---:|---:|---:|---:|
| 20k | 10.8mm | 22.4mm | 0.125N | 3.3% | 83.6% |

| 30k | 11.6mm | 39.8mm | 1.838N | 21.0% | 56.2% |

기존 영상45k의 대표 환경에서는5mm 이상 들림이 약38.84초 연속됐다. 새 힘 계측에서도 확인되어 단순 렌더링/발 인덱스 문제로 볼 수 없다. 28k는 FL도 일부 구간 들린다.

학습 범위 안의 중앙 EE/정지 평가에서도 주요 checkpoint의 RR 접촉률은 약3~6%였다. 10개 후보의 RR 평균 net force는 모두1N 미만이었다. 바닥 OOD만의 문제가 아니다. 기존 B1 45k 중앙 EE 정지 기록의 RR 접촉률은 약99.85%였고, AS2 초기 PD hold 검증은 네 발 모두접촉률100%였다. B1/AS2의 EE·하드웨어가 달라 엄밀한 원인 ablation은 아니지만, AS2가 기구적으로 네 발 지지를 할 수 없는 문제와 학습된 세 발 지지를 구분하는 근거다.

### 확인된 reward 빈틈

- **B1에서 사라진 중요한 신호:** 기존 B1 45k 정지 평가의 shaping force는 raw−0.4989×scale−2=weighted 약**+0.9977**, shaping velocity는 약**+0.4778**였다. 현재 AS2는 부호 수정과 정지 walking_mask로 둘 다0이다. Force 신호의 접촉 보상 역할을 제거한 뒤 정지 stance 대체항을 넣지 않은 것이 중요한 누락이다. Velocity 항목에는 원본의 cached foot velocity 읽기 문제도 있어 두 항목을 그대로 복원하는 것은 옳지 않다. 근거는 `reports/b1_contact_audit_20261111/flat_normal/result.json`과 원본 reward 함수다. 이 차이가 정확히 RR 해를 만들었는지는 독립 ablation 없이 확정하지 않는다.
- 정지에서 shaping force/vel은 walking_mask 때문에0. Feet height와air-time도0이다.
- Shaping을 정지에서 무작정 켜도 해결되지 않는다. Force 항목은 원래 swing 때 힘이 생기는 것을 벌하고, velocity 항목은 stance 때 발 속도를 벌한다. **공중에서 정지한 발은 속도가0이므로 접지 강제가 되지 않는다.**
- Force200N은 과도한 힘의 penalty 시작점이지, 힘0인 RR에 대한 penalty가 아니다. Drag도 접촉한 발만 평가하고 jerk는 변화량이므로, 정적으로 떠 있는 발을 직접 벌하지 않는다.
- `stand_still`은 네 발 지지가 아닌 기본 관절각과의 거리 보상이다. Roll이 작고 CoM이 지지 삼각형 안에 있으면 세 발로도 이들 지표를 만족할 수 있다.
- Body-contact termination도 기존대로 비활성이므로 reset0은 네 발 지지/무접촉 보증이 아니다.

따라서 정지 조작 mode에 **네 발의 지면 근접·유효 접촉·계획 stance 발 위치 유지·지지 여유**를 직접 요구해야 한다. 시뮬레이터 상태로 계산하는 reward이므로 실제 Foot Force Sensor를 policy 입력에 추가할 필요는 없다. 접지 하중을 무조건4등분할 필요는 없으며 전방 tilt에서 뒤 하중이 감소하는 것은 허용하되 RR을 공중에 방치하는 해를 억제해야 한다. 어떤 항목이 RR 선택을 주도했는지의 정량적 인과 분리는 후속 ablation이 필요하다.

예를 들어 `r_stop_support=−w_s·stop·mean_i(1−c_i)`의 missing-stance penalty와 발바닥 지면 간격 penalty를 별도로 둘 수 있다. `c_i`는 simulator의 부드러운 정상 접촉 score이며 입력 sensor가 아니다. 기존 보행 shaping의 잘못된 부호를 되살리지 않고 정지에서 잃은 지지 유인을 되돌리는 방식이다. 계수·접촉 판정값은 후속 기여도/rollout 비교로 정한다.

Rough의 net force 누락 때문에 접촉 score를 힘 하나로 확정하지 말고 발밑 지면 높이·실제 발 간격과 교차 검증해야 한다. 또한 강한 외란에서 필요한 회복 stepping까지 금지하는 hard constraint가 아니라, 정상 정지 조작의 지속적인 세 발 지지를 억제하는 task/contact-plan 항목으로 설계해야 한다.

## 3. 과속 penalty와 저속 제어

**과속을 벌하는 항목이 필요하다.** 현재 양의 vx command에서 `2×min(vx,v_cmd)/(v_cmd+eps)`라서 명령0.4일 때 실제0.4/0.6/0.8m/s가 모두 약+2다. 부족한 속도만 불리하고 과속은 다른 보상과 자유롭게 교환된다. 이 부분은 원본 B1에도 있던 설정이며 AS2 안정화를 이유로 대칭 추종을 새로 삭제한 것이 아니다.

우선 대안은 이미 존재하는 `tracking_lin_vel_x_exp`의 대칭 오차 추종으로 교체하거나 이를 활성화하는 것이다. 같은수식·가중2의 예시에서 실제0.4/0.6/0.8은2/0.736/0.271로 구분된다. 수식 비교일 뿐 이번에 적용하지 않았다.

Max 항목을 남긴다면 명령 방향의 초과 속도에 대한 hinge penalty `−λ[max(sign(v_cmd)vx−|v_cmd|−ε,0)/v_ref]²`를 추가할 수 있다. 정지와 역방향은 별도 처리해야 하며, 대칭 오차 reward가 충분하다면 중복 penalty를 무조건 늘릴 필요는 없다. λ/σ/허용오차는 실제 요구 속도와 reward 기여도·rollout 결과로 정해야 한다.

추가로 vy command0이어도 횡방향 추종/정지 penalty가 현재0이다. 기존 `penalty_lin_vel_y`는 scale0이고 활성화하더라도 큰yaw 명령에서는 함수 내부에서0으로 만드는 문제가 있다. **회전 때도 vy 오차를 평가하는 대칭 XY 추종**이 필요하다. Yaw는 이미 대칭 제곱 오차 기반 추종이 활성화되어 있으므로 같은 문제라고 설명하거나 무조건 중복항을 추가해서는 안 된다.

현재 clip/deadband는 vx0.2m/s·yaw0.5rad/s다. 두 명령이 모두 이보다 작으면 training command 자체가0으로 바뀌고, walking/stand 분기도 이 기준을 쓴다. **바닥 접근용 느린 creep와 작은 회전 명령을 충분히 학습한 설정이 아니다.** 실기 추정 노이즈와 작업 허용오차에 맞는 deadband 및 저속/정지 명령 분포가 필요하다. 수치를 임의 확정하지 않는다.

## 4. 전방 tilt와 보상의 충돌

고정 base-height target0.3244m, scale−5는 몸통을0.27m로 낮추면 약−0.272의 weighted 비용을 만든다. 반면 z방향 EE 오차10cm를0으로 줄이는 EE world reward의 개선은 `0.8×(1−exp(−0.2))≈+0.145`다. 다른 항목을 제외한 수식 비교지만 **높이 cost만으로도 그 EE 개선 이득을 넘을 수 있다**. 여기에 기본 자세 보상이 깊은 앞다리 crouch를 불리하게 만들 수 있다.

필요한 방향은 일반 보행/홈 자세의 높이·기본자세 보상을 보존하면서, 바닥 조작 mode에 검증한 몸통 높이 band 또는 task-dependent reference와 자세 reference를 사용하는 것이다. Pitch0 orientation penalty를 무조건 추가하면 원하는 전방 tilt를 막으므로 적합하지 않다. Roll·관절 한계·급격한 동작·몸통 충돌 제한은 유지해야 한다. 현재 `pitch_control=False`는 runtime controller에서 읽히지 않는 flag여서 이 값만 켜서 tilt를 학습시키는 해결책은 아니다.

## 6. 배포용으로 추가·수정할 우선순위

1. **목표 계약:** 실제 arm-base 관측 + 지면/물체 기준 world 목표 + tool orientation을 명시하고, 전방 바닥부터 상단까지 유효 전신 작업공간/경로를 검증한다. 목표 위치만 맞고 orientation은 모르는 입력 구조를 보완한다.
2. **정지 stance:** RR 포함 네 발 지지·발 위치 유지·접촉 지지 여유를 학습 목표로 넣고 base 명령0+고정 EE/이동 EE/바닥 EE에서 별도로 검증한다. 단순 reward 총합/roll/reset0으로 통과시키지 않는다.
3. **속도 정확성:** 양방향 vx·vy·yaw의 대칭 추종과 정지/저속 명령 분포를 맞춘다. 과속 hinge는 필요 시 보조. 두 축 모두 실제 오차를 기록한다.
4. **Task-dependent crouch:** 바닥 mode에 전방15~30° 등의 기구학 검증 자세와 높이0.27~0.30m 후보를 반영하고, 기존 높이/기본자세 cost와 목표 충돌을 제거한다. 최종 각도/높이·scale은 동적/토크 검증 후 확정한다.
5. **실제 actuator/자산:** 현재 D435i/마운트 포함 자산으로 새 실험을 고정한다. 손목 payload·PiPER 연속/피크 토크·gain·속도/가속 제한·지연 및 AS2 SDK 명령/관측 bridge를 실측/확인한다. DLS joint target clamp만으로 토크·속도·열 제한을 만족한다고 보지 않는다.
6. **파지와 상호작용:** 현재 두 손가락은 열림 유지다. 18action 계약을 유지하면서 별도 동기 그리퍼 명령, 물체/파지후 payload·접촉 반력·이동 중 회복을 포함해야 실제 ground picking을 검증할 수 있다.
7. **검증:** 새로운 목표/stance/reward의 짧은 PPO 검증 → hold-out 명령·목표·rough/마찰/질량/외란·지연·sim2sim → 실제 센서 입력/JIT/motor loop 정합과 단계적 실기 확인. 성공 기준은 작업 허용오차와 확인된 하드웨어 한계로 정하고, 네 발 지지·초과 속도·EE pose·실제 arm effort를 함께 기록한다.

현재 `legged_gym/scripts/b1z1_interface.py`도 Gym 환경을 만들어 `env.get_observations()/env.step()`으로 실행하는 시뮬레이터 interface다. AS2/PiPER 실물 센서→관측755/배포737 계약→joint 명령 송신 bridge가 완성된 것으로 볼 수 없다. JIT export 검사와 실물 배포 경로 검증은 구분해야 한다.

## 자산 변경과 재현성

현재 production URDF에는 별도 wrist-camera 통합 작업에서 D435i0.072kg + 마운트0.030276kg가 추가됐다. 총 명목 질량23.328064→23.430340kg다. 카메라/브라켓 관성은 문서의 잠정 시뮬레이션 값이며 실측 정격으로 단정하지 않는다. 이번 작업은 이를 수정하지 않았다.

기존 run의 URDF hash는 `d0d667...`, 현재 카메라 포함 파일은 `8df7e...`여서 원래 평가의 hash guard가 올바르게 중단했다. 원본 exact-byte backup을 report 내부 shadow asset으로 사용해 기존 현상만 재평가했고, 현재 자산은 workspace 계산에 사용했다. 기존 링크·조인트 파라미터가 보존된 카메라 append임도 검사했다. 과거 checkpoint를 새 손목 payload가 포함된 자산에서 학습한 것으로 간주하면 안 된다.
